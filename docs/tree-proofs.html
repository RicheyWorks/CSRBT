One · the potential function

A bound that is false every time and true in the end

A splay tree makes no promise about any single operation. Touch the deepest node and you pay for its depth. What Sleator and Tarjan proved in 1985 is that you cannot keep paying: an expensive access flattens the path it walked, so the next one is cheap. The accounting that makes this rigorous is a single function of the tree's shape.

Φ(T) = Σx ∈ T log₂ size(x)

Define the amortized cost of an operation as its actual cost plus the change in Φ. Because Φ depends only on the tree and not on history, summing over any sequence telescopes — every intermediate Φ cancels:

Σ aᵢ = Σ cᵢ + Φ(Tₙ) − Φ(T₀)

So a bound on each amortized cost is a bound on the whole sequence, give or take the potential you started and finished with. Sleator and Tarjan's Access Lemma gives that bound: splaying x to the root costs at most 3(log₂size(root) − log₂size(x)) + 1 amortized — O(log n), whatever the tree looks like.

Read the picture, not the numbers. The bars are what each access really cost in rotations. The line is actual + ΔΦ. Two things are worth doing in order.

Press “Worst case”, then access key 1. The tree is a left-leaning path of 63 nodes — the shape balancing exists to prevent — and key 1 sits at the bottom of it. What happens is worth reading twice:

63 rotations. A genuinely terrible access, the worst this tree has.
Φ falls from 290.0 to 149.6. The splay did not merely find the key; it destroyed the path it walked.
Amortized cost: −77.4. Negative. Against a bound of 3·log₂(63) + 1 = 18.9, the operation came in seventy-seven units under budget — it paid for itself and left change.
Access the same key again: 1 rotation.

That is what the potential function is for. The 63 rotations were real and you really paid them — but you had been charged for that path in advance, every time an earlier operation left the tree a little worse. The accounting only looks like magic if you arrive at the expensive operation without having watched the bill accumulate.

Then press “Sequential” on a fresh tree and watch the opposite: cheap accesses whose amortized cost runs above the bar, because each one leaves the tree more path-like than it found it and Φ climbs. That is the theorem being honest with you — amortized analysis is not a trick for making costs look smaller, it is an accounting system, and it charges you for the mess you leave behind as surely as it credits you for the mess you clean up.

What this page will not claim. The identity above is exact and this page checks it after every operation. The Access Lemma is a theorem and is cited, not re-derived here — watching a bound hold on one tree is evidence, not proof, and the difference is the whole point of having a proof. Sleator & Tarjan 1985, JACM 32(3)

Two · the worst tree allowed

AVL's height bound is a Fibonacci number

An AVL tree permits a height difference of one at every node. Ask the natural question — what is the sparsest tree that rule allows? — and the answer builds itself: to make a minimal AVL tree of height h, hang a minimal tree of height h−1 on one side and h−2 on the other.

N(h) = N(h−1) + N(h−2) + 1,   N(0) = 0, N(1) = 1

That recurrence is Fibonacci with an offset: N(h) = F(h+2) − 1. Because the minimum node count grows exponentially in the height, the height grows logarithmically in the nodes — and inverting the closed form gives the classical bound.

h ≤ 1.4404 · log₂(n + 2) − 0.3277

Built for real: the recurrence is used to construct an actual AVL-valid tree, then the tree is measured. If the identity failed, the row would say so.

Three · an old tree in a new coat

Every red-black tree is a 2-3-4 tree

The red-black rules look arbitrary until you see what they encode. Take any red-black tree and absorb every red node into its black parent. What is left is a tree in which each node holds one, two or three keys and has two, three or four children — and in which every leaf is at exactly the same depth. The colours are a way of storing a perfectly balanced multi-way tree in a binary one.

The height bound falls straight out. The 2-3-4 tree is perfectly balanced, so its height is at most log₂(n+1). Each of its levels becomes at most two binary levels — a black node and its red children. Hence:

h ≤ 2 · log₂(n + 1)

Four · a parameter that had to be proved

Why this engine ships Δ = 3, Γ = 2

A weight-balanced tree balances by size, not height: at each node, neither subtree may outweigh the other by more than a factor Δ, and Γ decides whether a violation is repaired with a single rotation or a double one. Both are free parameters, and for thirty years people picked them by taste.

They are not free. Hirai and Yamamoto showed in 2011 that the pairs which keep the invariant through both insertion and deletion form a bounded region whose boundary is nine lines and a curve — and that (3, 2) is the only pair of integers inside it. Hirai & Yamamoto 2011, JFP 21(3)

This is not a theoretical nicety. The bug report that prompted the work was a real one: a widely used implementation running Δ = 5, Γ = 1 broke its own balance invariant after a deletion — a counterexample, not a slow path.

The part worth telling. This engine's evolutionary search (ADR-011) was pointed at the same parameter space with no knowledge of the proof. It converged on Δ = 3, and unsound points such as (5, 3) disqualified themselves against the health gate on the record. A search that arrives where the proof already is, is not a discovery — but it is a good sign that the gate is measuring something real.

Five · what one extra integer buys

Rank in O(log n), from a number you were already maintaining

Store in every node the size of its own subtree — one integer, kept correct through rotations at no asymptotic cost. That single augmentation turns a set into an ordered set: the k-th smallest element, the rank of a key, the median, any percentile, all in one root-to-leaf descent.

The descent is the whole algorithm. At each node, everything in the left subtree is smaller, so the node's own rank is size(left) + 1 within its subtree. Go left and the answer is unchanged; go right and you have skipped size(left) + 1 keys, so carry them.

The same descent run the other way gives rank(key), and select(⌈n/2⌉) is the median. In a hash set or a plain balanced tree without the augment, each of these is O(n).

Everything computed on this page runs in your browser from the tree in front of you — no network, no server, no stored answers. The balancing is reimplemented from csrbt-core/strategy and checks its own invariants after every operation; if a check ever fails, the page says so rather than drawing a picture anyway.

# ADR-192 — HTTP: the first transport anything else can reach

**Status:** accepted · **Date:** 2026-09-12 · **The fifth of the seven slices of `docs/PLAN-operator-api-2026-09-11.md`. `tools/harness_http.py` serves the same gateway over streamable HTTP — POST for messages, an SSE stream for notifications, a bearer token, a session id — and it imports `harness_mcp.Server` rather than reimplementing it, which is ADR-102's claim about where the boundary is, put under load. The **official MCP Python SDK**, which has never seen this repository, now connects to it and drives the collection sheet end to end; its trace is kept in `tools/traces/http/`. That connection found a defect nobody had ever been able to see: Playwright's synchronous API is bound to the thread that made it, and an HTTP server answers each request on a new one. New suite `verify_http` 65, new runner `mutate_http` 26/26.**

## 1. What a pipe could not do

Two transports, and both are spoken to by the process that launched them. That
is fine for `verify_walk` and for `blind_console`, and it is exactly the wrong
shape for the thing the operator API is for. Every host that matters — a
desktop app's remote servers, an IDE, an agent runtime, anything that did not
start this container — connects over HTTP.

    POST   /mcp   a JSON-RPC message, or a batch
    GET    /mcp   an SSE stream for server → client notifications
    DELETE /mcp   end the session

The whole of the file that is not HTTP is one import:

    from harness_mcp import Server

`Server.handle` is the only thing that knows what `tools/call` means, and the
suite holds that the HTTP layer names **none of the four operations** — the
one method name it knows is `initialize`, and only because the specification
puts the session id there. ADR-102 said a transport "maps four operations and
decides nothing" in 2026; a second transport that had to re-derive any of them
would have shown the boundary was in the wrong place.

## 2. Three things a socket owes that a pipe does not

**A second switch.** The kit has been off-unless-switched-on since ADR-101:
`CSRBT_HARNESS_ENABLED` and a 24-character token. A listening socket is a
larger thing than a pipe — a pipe can be written to only by whoever opened it,
a port by anything that can reach it — so this takes `CSRBT_HARNESS_HTTP=true`
as well. Nobody opens a network door by copying a stdio command line.

**Loopback.** It binds `127.0.0.1`. Binding anywhere else takes
`CSRBT_HARNESS_HTTP_BIND` naming the address, and the server says on stderr
that it did and what that means. The specification says a local server SHOULD
bind localhost; a door with MUTATE behind it should have to be *asked*.

**Origin.** Every request's `Origin` is checked and a page that is not
loopback is refused. This is the one attack a localhost-only server is still
open to — the attacker's javascript runs in a browser that can reach
`127.0.0.1` — and the check is on the **parsed hostname**, not on the string,
because `http://127.0.0.1.evil.example` contains a loopback address and is not
one. A request with *no* Origin is a non-browser client and is allowed; that
is what the header's absence means.

## 3. One session, and it says so

This door fronts one browser page. Two hosts driving one page is not a smaller
version of two hosts driving two pages — it is two operators typing into the
same form, which is the thing ADR-191's console session already forbade. The
first `initialize` claims the session and is issued an id in
`Mcp-Session-Id`; a second is **409**, with the reason. An id this server did
not issue is **404**, which is the specification's way of saying "initialize
again" and is the right answer for an id from a door that has since restarted.

## 4. The thread

The first time the official SDK asked for the collection sheet it got this:

    {"ready": false, "why": "Cannot switch to a different thread\n
      Current:  <greenlet.greenlet object at 0x7fb5e8726300 …>
      Expected: <greenlet.greenlet object at 0x7fb5e93e5040 …>"}

`ThreadingHTTPServer` answers each request on a new thread. Playwright's
synchronous API may only be driven from the thread that created it. Over
stdio there was never a second thread, so in ninety-odd ADRs nothing had ever
exercised it — a defect this transport revealed rather than caused, and the
plainest possible argument for connecting something you did not write.

It is fixed where it belongs. `Door.pump()` runs on the thread that stood the
target up — the caller of `serve()` — and every gateway call is handed back to
it; the listener runs on a thread of its own. The target is driven serially by
one thread whatever the socket does, which is what "one session, one target"
already meant and is now enforced rather than assumed.

`verify_http` holds it with a target that behaves the way Playwright does: six
requests fired *at once*, from six client threads, at a plugin that raises if
touched from any thread but the first. The first version of that check used
`threading.get_ident()` and passed against the broken door, because a dead
thread's ident is handed to the next one. It counts thread *names* now.

## 5. The first external host

Every trace this kit holds was taken through `tools/blind_console.py` — a
client written in this repository, by the same hand as the door it talks to.
That is the right instrument for a blind trial and the wrong evidence for "an
external host can connect", because a client that shares an author with its
server can agree with it about anything.

`tools/traces/http/collection-sheet-sdk.jsonl` was taken by the **official MCP
Python SDK** (`pip install mcp`), which implements the specification rather
than this door and negotiated `2025-03-26` with it. Seven recorded calls on
the collection sheet, every one answered first time:

| call | answer |
|---|---|
| the snapshot | 307 controls, stamp `s31f870317da8` |
| `pick` Agaricus | **2 067 bytes of diff** where the snapshot is ~100 000 |
| `?since=<stamp>` | `changed: false` |
| `set_text` `#cName` | `changed: true`, `#cName` altered — ADR-191's value publication, over HTTP, through a client that knows nothing about either |
| `show_pane` `p-met` | `route: p-rec → p-met` |
| `read_report` | 15 boxes, 35 rules |

Nothing in `tools/` was changed to make the SDK work. One thing in `tools/`
was changed because it did not, and that is §4.

`verify_http` section D re-runs that session when the SDK is installed, and
prints `NOT VERIFIED` — one line per claim, so the suite's total does not
change — when it is not. A check that silently skips is worse than one that
admits it did not run.

## Held

- A notice is **never discarded because of an Accept header**. With a GET
  stream open, notifications go there; without one they ride the POST that
  caused them, as an event stream, ahead of its answer (ADR-137's ordering).
  A client that did not say it takes a stream gets the one JSON object it
  asked for, the notices go back on the queue, and
  `Mcp-Notifications-Pending` says how many are waiting.
- One notification stream per session. Two readers of one queue is a notice
  that reaches one of them.
- An oversized body is **drained, bounded, then refused**. Answering without
  reading leaves the sender writing into a socket nobody is reading, which it
  sees as a broken pipe rather than as the 413 it was sent.
- The suite may not be hangable by its own subject. A door that answers a
  request it should have refused by opening an endless stream would hang
  `verify_http` rather than fail it — and a suite its subject can hang cannot
  be used to break that subject on purpose. Every check that could meet a
  stream carries a timeout shorter than the stream's heartbeat, and the
  runner reports a mutant that hangs the suite as inconclusive rather than
  dying with it.
- No page, no task and no plugin was edited. The gateway, the contract and
  the two existing transports are byte for byte what ADR-191 left.
